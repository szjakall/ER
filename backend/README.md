# ER 图规则校验后端（B）

按 `INTERFACE.md` 协议实现的 ER 图实时校验服务：
**字典树索引 44 条规则 → WebSocket 实时校验 → 返回 violations（红）/ suggestions（橙）**

---

## 快速开始

```bash
cd backend

# 启动服务（默认 ws://localhost:8000/ws，与 INTERFACE.md 一致）
python server.py

# 若 8000 被其他程序占用（0.0.0.0:8000 已被占），
# 可只绑回环地址，仍然对外提供 ws://localhost:8000/ws：
python server.py --host 127.0.0.1 --port 8000

# 或整体换端口：
python server.py --port 8010
```

> **端口冲突说明**：本机 `0.0.0.0:8000` 曾被另一项目
> （`exp\evil_server.py`，非本项目进程）占用。
> 由于 `localhost` 解析到 `127.0.0.1`，用 `--host 127.0.0.1 --port 8000`
> 即可在**完全不影响该进程**的前提下，提供约定的 `ws://localhost:8000/ws`。
> 上表基准数据即在 `127.0.0.1:8000` 上实测所得。

前端切换到真实后端时，把 WebSocket 地址指向本服务即可，
**前端与 mock 均无需改动**（协议完全一致）。

## 薄弱点记录与学情接口（研究内容三）

对应需求书：「自动记录违规信息（用户标识、错误类型、触发时间、错误次数、
设计上下文），会话结束后生成个人错误清单，按错误类型分类汇总，标记高频薄弱点。」

**数据来源**：每次校验完成后由引擎自动记账，**O(1) 写入**，实测单次开销
**0.0085ms**（相对 <100ms 预算可忽略）。

**学生标识怎么来**（重要）：
1. 连接时带查询参数（推荐）：
   `ws://localhost:8000/ws?user_id=2023001`
2. 或在消息体里带 `user_id` / `student_id` 字段
3. 都不传 → 退化为连接标识（可记录，但**教师无法按学生查询**）

### HTTP 接口

| 接口 | 用途 |
|---|---|
| `GET /weakness/{user_id}` | 个人错误清单：按规则分类汇总 + 高频薄弱点 |
| `GET /weakness` | 班级学情：共性问题识别（如"80% 学生遗漏基数标注"） |
| `DELETE /weakness/{user_id}` | 清除某学生记录（会话归档后调用） |

**排序口径（v1.4 修正）**：班级共性问题按**学生命中数**降序
（教师关心"多少人中招"，需求书"80% 学生遗漏…"即此语义）；
平局依次按总记录数、规则号，排序稳定可测试。
个人薄弱点 `weak_points` 是 **top-3 截断**（`?top_n=` 可调），
平局按首次出现顺序——**它不是"该学生的全部薄弱点"**，取的是最值得看的几条。

**个人清单返回示例**（实测）：

```json
{
  "user_id": "e2e-weakness-student",
  "total": 13,
  "error_count": 5,
  "warning_count": 8,
  "by_rule": [
    { "rule_id": "R02", "level": "error", "count": 3,
      "message": "实体'实体0'缺少主键标注 —— 请在属性名前加 * 号",
      "first_at": 1762942000.1, "last_at": 1762942010.4 }
  ],
  "weak_points": [ { "rule_id": "R02", "count": 3, "share": 0.231 } ],
  "session_span_sec": 42.3
}
```

**班级学情返回示例**：

```json
{
  "student_count": 32,
  "common_issues": [
    { "rule_id": "R14", "level": "error",
      "message": "联系连线缺少基数符号（请在线上写 1 / N / M / P）",
      "total_count": 41, "student_count": 26, "student_share": 0.812 }
  ]
}
```

> **去重窗口**：同一 (学生, 规则, 元素) 在 3 秒内重复触发只计 1 次。
> 否则学生拖拽元素时，同一条错误会在每次 `element_modified` 里重复触发，
> 统计会严重失真（错误次数被放大几十倍）。
>
> **内存保护**：每人最多保留 2000 条记录、去重表 4096 条，
> 超出后丢弃最旧的一半，避免长会话内存无限增长。

### 持久化（服务重启不丢学情）

台账默认落盘到 `backend/weakness_log.jsonl`（JSONL 追加写），
服务重启时自动回放，**学情数据不会因重启丢失**。

| 环境变量 | 作用 |
|---|---|
| （默认） | 落盘到 `backend/weakness_log.jsonl` |
| `ER_WEAKNESS_LOG=<path>` | 指定日志路径 |
| `ER_WEAKNESS_LOG=""` | 关闭持久化（仅内存） |
| `ER_TESTING=1` | 测试模式：不落盘（审计脚本已自动设置） |

**为什么选 JSONL 而不是数据库**：追加写不阻塞、零额外依赖、崩溃最多丢尾部缓冲；
对本场景（高频小额写入 + 低频查询）足够。若将来要多实例并发查询，再换 SQLite。

> ⚠️ **部署约束（实测）：必须单实例运行。**
> 两进程并发写同一 JSONL 的实测结果是**静默丢行**——
> 两实例各写 50 条，最终只剩 82 行且无损坏痕迹（Windows append 模式
> 文件位置独立，互相覆盖）。多实例部署会悄悄丢学情数据。
> 若确需多实例（如分机房负载），请改用 SQLite 或集中式存储。

**WS 消息上限**：单条消息 ~1MB（uvicorn 默认），超限会被服务端以
1009 关闭——这是库级资源保护（前端 `ws.ts` onclose 自动重连恢复）。
正常绘图消息 <10KB，余量充裕。二进制帧不会断连（回 error 响应）。

**写入策略**：缓冲 **32 条**批量落盘（首次写入立即落盘以建立文件），
断连时与进程退出时强制 flush。

| 写入方式 | 单条开销 |
|---|---|
| 逐条 open/write | 715 μs |
| **缓冲批量写** | **39.7 μs**（快 17.9 倍） |

> 缓冲策略的固有代价是"必须记得 flush"。已做三重保障：
> ① 断连时 flush ② 进程退出时 flush ③ `__del__` 兜底。
> 落盘失败只计数（`persist_failures`），**绝不影响实时校验**。

## LLM 深度归因（研究内容三的"LLM 归因"部分）

对应需求书：「将学生的错误历史、错误类型分布、设计上下文输入大模型，
生成自然语言诊断报告」以及「规则引擎优先、**LLM 异步增强**」。

### 三层结构

```
规则引擎（engine.py）          毫秒级实时校验，绝不等待 LLM
      │ 统计信号达标才投递（O(1)）
      ▼
异步队列（diagnose_queue.py）  后台 worker 串行消费，不阻塞绘图
      │ 生成完成
      ▼
归因器（llm.py）               生成诊断报告
      │ 回调
      ▼
WebSocket 推送                  action="diagnosis"，非侵入式提示
```

### 触发条件（不是每次操作都调模型）

| 条件 | 值 | 理由 |
|---|---|---|
| 累计违规数 | ≥ 5 条 | 数据太少无法归因 |
| 某规则重复次数 | ≥ 3 次 | 重复才说明是**概念问题**而非偶发疏忽 |
| 同一学生冷却 | 60 秒 | 防抖，避免反复调用 |

队列满（默认 64）时**丢弃最旧任务**，保证不堆积。

### Provider 抽象：为什么默认不依赖外部大模型

教学场景常在**离线/内网**环境，且需求书要求"开源模型本地部署"（形态未定）。
硬依赖会让功能在无模型时完全不可用。故：

| Provider | 何时启用 | 特点 |
|---|---|---|
| `heuristic` | **默认兜底** | 本地确定性归因，结合 44 条规则的教学知识点库；无需网络 |
| `llm`（OpenAI 兼容） | 配了环境变量 | 适配 Ollama / vLLM / LM Studio 等 |

```bash
# Linux / macOS（bash）
export ER_LLM_BASE_URL=http://localhost:11434/v1
export ER_LLM_API_KEY=not-needed
export ER_LLM_MODEL=qwen2.5:14b
```

```powershell
# Windows（PowerShell）
$env:ER_LLM_BASE_URL = "http://localhost:11434/v1"
$env:ER_LLM_API_KEY = "not-needed"
$env:ER_LLM_MODEL = "qwen2.5:14b"
```

**LLM 调用失败会自动降级**回启发式，诊断永不整体失败；
降级后在 `source` 字段标明来源，便于教师判断可信度
（需求书要求"保留教师复核空间"）。

> ⚠️ 需要说明：**本地启发式不是"假装的大模型"**，它是确定性的
> 教育领域归因（规则知识点 + 统计特征），可靠性高于大模型但语义深度有限。
> 真实 LLM 是可选增强，不是功能前提。当前环境未配置 LLM，
> 所以实测输出的 `source` 均为 `heuristic`。

### 接口

| 接口 | 用途 |
|---|---|
| `GET /diagnosis/{user_id}` | 个人学情诊断报告（可加 `?source=heuristic\|llm`） |
| `GET /diagnosis` | 班级学情摘要 + 教学调整建议 |
| `GET /diagnosis/queue/stats` | 异步队列状态（确认不阻塞） |
| WS `action="diagnosis"` | 诊断完成后非侵入式推送 |

### 性能（关键：不阻塞实时校验）

| 指标 | 实测 |
|---|---|
| 投递任务耗时 | p95 **2.2 μs**（worker 未运行也不阻塞） |
| `should_trigger` 判定（热路径每条消息都调） | **0.80 μs，且不随记录数增长** |
| 开启自动诊断后的校验延迟增量（handle 完整路径，配对测量） | **+0.02 ~ +0.06 ms**（4 次连跑稳定） |
| 本地启发式生成诊断 | **0.09 ms** |

**热路径 O(1) 优化记录**：
`should_trigger` 原先在每次判定时跑 `summary()`（O(记录数)），
实测学生积累 2000 条记录后**每条绘图消息要多花 1.15ms**，随错误累积线性变差。
已改为 `WeaknessTracker` 维护轻量计数器（`_rule_counts`，在 `record()` 时 O(1) 增量维护，
裁剪/回放时重算），触发判定全程 O(1)/O(规则数)——2000 条记录时仍是 0.80μs，**提速约 1500 倍**。

引擎纯计算（无网络）：

| 场景 | p50 | p95 | p99 |
|---|---|---|---|
| `element_added` | 0.38ms | 0.64ms | 0.83ms |
| `connection_added` | 0.25ms | 0.43ms | 0.63ms |
| `element_deleted` | 0.19ms | 0.36ms | 0.48ms |
| `batch_check`（整图 14 元素） | 0.44ms | 0.65ms | 0.80ms |

> 以上为 v1.3 规则（含 ISA 名称识别、多级弱实体 BFS）实测值，
> 较 v1.1 略增 ~0.1ms，预算 <100ms 下可忽略。

端到端 WebSocket 往返（`ws://127.0.0.1:8000/ws` 真实服务，前端实际感知延迟）：

| 场景 | p50 | p95 | p99 |
|---|---|---|---|
| `element_added` | 11.9ms | 28.6ms | 32.7ms |
| `connection_added` | 41.4ms | **58.6ms** | 64.3ms |
| `batch_check` | 1.1ms | 1.5ms | 1.9ms |

并发（20 个学生同时画图）：p50 10.4ms，p95 17.0ms。
单连接高频连续修改（模拟快速拖拽）：p95 0.8ms。

大图 `batch_check` 实测（邻接索引优化后）：

| 规模 | 耗时 |
|---|---|
| 200 实体 | 14.1ms |
| 500 实体 | 31.8ms |
| 800 实体 | 62.3ms |

**结论：单笔绘图操作 p95 均在 100ms 预算内，最紧的 `connection_added` 有约 41% 余量。**

**超大图（1000 元素）实测**（v1.4 补充）：

| 指标 | 实测 |
|---|---|
| 单元素事件 p95 | 2.17ms |
| `graph_fingerprint` 单次（每条消息都要构建） | 1.85ms |

## 关于「字典树保证 <100ms」的实测结论

需求原文设想是"用字典树索引规则以保证 <100ms"。实测后需要如实说明：

1. **44 条规则规模下，字典树本身不是延迟的决定因**。
   强制全量跑 44 条只需 0.36ms，字典树子集 0.31ms，加速比仅 1.15x。
   瓶颈从来不在"查找规则"，而在规则函数体。

2. **真正让索引见效的是"图指纹"优化**：若本次事件未改变图结构
   （例如只改标签文本），图结构级规则的结果必然不变，直接跳过。
   此时 44 条 → 16 条，加速比 **1.87x**。

3. **端到端延迟的大头是 WebSocket + JSON 序列化（12–57ms），
   而非规则计算（0.2–0.6ms）**，两者相差约 100 倍。
   所以若要进一步压延迟，应优化序列化与传输，而不是继续优化规则查找。

字典树仍然保留，理由是：它使"按事件族挂载规则"与后续规则库
扩充（几十 → 几百条）时的索引结构清晰，且在 `batch_check` 与
增量检查之间提供了统一的分派入口。
